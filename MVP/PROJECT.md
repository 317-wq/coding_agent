## 1. 项目概述

- 一句话描述：一个在本地工作区里读代码、按指令修改文件的命令行 Coding Agent。
- 解决什么问题：把"读代码 → 定位 → 改 → 确认落盘"这条链路自动化，人只负责下达任务和确认。
- 目标用户 / 使用场景：开发者在本地仓库里用小任务驱动 Agent 改代码。

## 2. 总体架构

- 架构图：见 `diagram/系统架构设计图.png`（完整目标架构，含远期模块）。
- 模块清单：

| 模块 | 职责 |
|---|---|
| 交互层（CLI） | 命令入口，接收任务、展示结果、处理用户授权与确认 |
| Agent 核心控制层 | 任务管理、复杂度判断、结构化规划、执行循环、上下文与完成判定 |
| 工具系统 | 工具注册、参数校验、策略检查、授权、统一执行；内置文件/搜索/测试/Git/命令工具 |
| 记忆系统 | 记忆管理与检索，含任务、项目、经验、用户四类记忆（远期） |
| 项目探索器 | 扫描项目结构、分析代码架构、提取项目信息 |
| 回滚模块 | 保存工作区快照、恢复到稳定状态、回滚后重新规划（远期） |
| 评测模块 | 分析 Trace、计算成功率、生成评测报告（远期） |
| 执行追踪 | 事件记录、耗时与调用统计、错误分析 |
| 公共支撑 | 配置管理、执行追踪、错误处理与恢复、安全边界控制 |

- 关键数据流：用户任务 → CLI → Agent 核心 →（工具系统 / 模型适配）→ 结果回灌 → 输出与 Trace 记录。

> 完整架构图包含远期模块，但各版本只实现当前需要的部分。

| 开发语言 | Python | 适合快速实现 Agent 核心逻辑 |

| 测试 | pytest | 覆盖模块、异常与集成流程 |
| 执行追踪 | logging + 自定义 Trace | 为调试、评测、问题分析提供数据 |
| 代码规范 | Ruff | 检查与格式统一 |

## 4. 长期接口约定

> 只定接口边界，具体字段、参数、节点拆法放 MVP。

- CLI 入口：通过 `coding-agent` 项目命令或 `python -m app.cli.main` 启动；使用 Typer 定义和校验参数，使用 prompt_toolkit 接收支持多行粘贴的终端输入，使用 Rich 渲染交互状态与文本报告。交互终端以 Enter 提交、Shift+Enter 或 Alt+Enter 换行；非交互式管道输入继续使用 `END` 分隔任务。
- Model Adapter：接收消息与调用参数，返回统一格式的模型响应；按 `QWEN_CHAT_MODEL_1` 至 `QWEN_CHAT_MODEL_10` 的已配置顺序选择候选，仅在额度、限流、模型缺失或不可用错误时切换，并持续复用最近成功模型，非可用性错误不得盲目切换。
- 工具系统：通过工具注册表按名称查找工具，校验参数后执行，并返回包含状态、结果和错误信息的结构化结果；高风险工具必须经过授权。
- Agent 核心：根据模型响应和工具执行结果推进任务，并维护上下文与完成判定。
- Agent 任务结果：每次任务结束后生成结构化 `TaskResult`，通过 `agent.last_result` 提供给 CLI 和后续调用方；保留字符串返回值用于兼容旧调用方。
- 最终状态核验：生成 `TaskResult` 前必须重新读取任务触碰文件的内容摘要、最终 Git 工作区状态、真实测试调用结果和 Trace 调用统计；报告中的变更、测试、调用次数和完成状态只能来自这些结构化证据，模型自由文本不得作为事实来源，核验失败时任务必须降级为阻塞。
- Planner：接收用户任务与项目快照，按阅读、实现、测试编写、测试执行等实际开发目标返回可序列化的有序步骤计划；“代码修改后重跑测试”等恢复描述不得误生成测试编写步骤；步骤状态由 Agent 核心依据工具能力、目标路径和完成条件维护，不按工具调用顺序机械推进，多文件实现和多用例测试编写在首次写入后保持 `running`，分别在进入测试编写和测试执行阶段时完成；后续阶段工具即使失败也证明阶段已经切换，失败应归属于新阶段，不得把已结束的前一阶段重置为待处理；成功删除用户明确指定的遗留文件可完成实现或修改步骤；失败恢复重规划时，目标和完成条件一致的已完成步骤必须继承，只有失败或未完成步骤重新执行；初始无计划的简单任务首次恢复时直接建立新计划，不得对空计划执行步骤继承。
- 上下文管理：维护用户任务、项目快照、任务计划、工具结果和测试结果，并在达到限制时压缩单条长证据、去除重复任务文本及裁剪较旧非关键内容；工具失败触发重规划后，失败证据保留在 Trace 中但不再永久污染新计划的完成判定，测试失败则继续按测试目标保留至成功重跑或阻塞结束。
- 完成判定：结合计划完成条件、工具结果和测试结果判断任务是否完成，不以模型文字回复作为唯一依据；同一测试目标修复后的最新结果覆盖该目标的旧结果，父级文件、目录或全工作区测试成功也覆盖其子目标的历史失败，其他目标的失败证据继续保留。
- 完成判定约束：所有必要计划步骤必须实际完成；测试通过不得覆盖其他 pending 步骤，失败或取消的工具结果必须判为阻塞并保留待处理步骤与失败证据。
- 轮次上限收尾：最后一个允许轮次若通过工具结果完成全部计划、测试和明确需求，Agent 必须直接执行确定性完成核验并结束，不得因缺少额外的模型总结轮次误报 `max_steps`。
- Git 工具：只提供仓库识别、状态和差异读取能力；不通过模型直接执行提交、重置、切换或清理操作；工作区不是 Git 仓库时返回明确的无可用 Git 信息结果，不得把这一环境事实当作工具失败并触发恢复或回滚。
- 变更快照：任务开始后按需记录 Agent 将要修改的路径及其原始状态，仅覆盖本次任务触碰的文件；写前快照是回滚保护基线，不代表工具已成功修改，Trace 仅在观察到实际文件变化时关联记录 `snapshot_created` 和 `mutation_applied`。
- 变更集口径：`ChangeSet` 实时表示当前文件相对于本任务首次触碰前状态的净变化；`changed_count` / `net_changed_count` 和各类路径只统计当前仍存在的差异，触碰后恢复原状的路径计入 `unchanged_count`。
- 失败恢复：根据工具失败、测试失败类型和完成判定结果生成恢复决策；单次计划步骤失败时保留已有修改并先重新规划，只有连续工具失败达到阈值或确定阻塞时才建议回滚；项目代码导入错误、循环导入、测试代码错误和可修复的收集错误必须保留失败证据并进入“分析 → 修改 → 重跑”流程，pytest 未发现测试必须单独分类并允许先编写测试，不得误判为断言失败；只有上一测试结果仍然失败时，业务实现修改后的测试重跑才计入最多两轮的修复额度，单纯修正测试脚手架或测试已通过后的普通完善不占用额度；修改代次只在磁盘真实发生变化时推进，同一测试失败后没有新修改时禁止原样重跑；失败测试后已有实际修改但尚未重跑时，模型总结不得结束任务，且下一轮请求只向模型暴露 `run_tests` 并要求重跑原测试目标，避免重复读取、继续编辑或创建旁路文件耗尽轮数；两次测试修复仍失败且用户授权回滚后必须停止任务，不得从初始状态重复整项任务；若失败与用户约束冲突或无法安全修复，保留已有有效修改并以 `blocked` 结束，不因旧失败回滚已经验证有效的修复；只有缺少测试运行器、超时等真实环境错误才直接停止；回滚必须经过明确授权，并恢复到任务修改前状态后再决定是否重新规划；回滚成功后必须再次比较磁盘状态与任务初始快照，确认净变化为零后才能重置变更会话和测试失败状态；用户拒绝回滚时立即保留当前修改并请求后续确认，不清空上下文或重建计划，拒绝回滚的保留路径不标记为恢复失败。
- 项目工作区：由 CLI 指定并在启动时解析为受控根目录，所有文件工具只能访问该目录。
- 文件操作：必须遵守工作区边界，禁止越界读写；模型调用文件工具时使用工作区相对路径，根目录使用 `.`，工具可安全归一化工作区自身绝对路径。
- 路径规范化：所有文件、搜索、测试和 Git 工具共享 `WorkspaceContext` 的解析规则；输出使用保留真实文件名与扩展名的工作区相对 POSIX 路径，不猜测或补全文件名；测试工具支持 `file.py::Class::test` pytest node id，安全边界校验只解析其文件路径部分并完整保留节点后缀。
- 批量工具调用：同一模型响应中的工具按顺序执行；任一调用失败或取消后立即中断该批次剩余调用，只有成功结果允许继续执行下一调用。
- 重复写操作：Agent 对任务内已成功的相同写操作先核对当前文件状态；目标状态仍成立时复用原结果而不再次写盘、推进计划或触发恢复，状态已变化时才允许重新执行；对本任务刚创建文件的不同内容二次 `create_file` 必须重定向模型使用 `edit_file`，不得作为工具失败触发回滚。`edit_file` 对目标文本已存在的重复替换返回幂等成功。
- 开发阶段工具约束：开发计划仍有实现或测试编写目标且工作区不存在测试源文件时，不向模型暴露 `run_tests`；成功的文件创建和编辑必须在工具返回前核验落盘，重复写操作不消耗实际工具调用预算，并返回明确的幂等提示。
- 执行轨迹：以结构化事件记录，供调试与评测使用；同一任务共享稳定 `trace_id`，事件携带递增序号，模型请求、工具调用、完成判定和恢复流程分别通过关联 ID 串联；安全策略拒绝必须记录独立 `safety_rejected` 事件和明确原因，未触发动作的常规 `continue` 恢复决策不重复输出。CLI 默认仅将关键事件渲染为简洁进度，完整 Trace、模型轮次和工具日志仅在启用 `--debug` 时输出，静默显示不影响结构化事件留存。
- 用户约束：任务级只读/禁止文件变更约束必须在整个 Agent 执行循环中生效；工作区边界违规属于不可恢复安全错误，立即停止任务，不得继续调用工具。
- 验收任务控制：安全边界、越界路径、完成状态以及不含肯定开发动作的最终验收任务使用轻量执行路径；首次失败或证据不足即停止，不生成无关开发计划，不重复重规划或扩展测试范围；识别前必须剔除“不修改代码”等否定动作和“自动修复次数”等报告元数据，完整开发任务仅在章节中出现“验收标准”“验证”等字样时不得误判为一次性验收。
- 计划证据：创建目录只视为文件写入的前置条件，不得据此完成实现或测试编写步骤；`tests/__init__.py` 等测试目录辅助文件也不得作为测试用例完成证据，只有 `test_*.py` 或 `conftest.py` 可匹配测试编写步骤；创建、实现、修改、修复和新增等开发目标必须由实际文件写入结果匹配。
- 明确需求核验：从任务文本提取文件要求时必须保留完整工作区相对路径，包括多层嵌套目录；模块清单中的裸 Python 文件名和明确指定的 `argparse` 等实现框架也必须在结束前核验，不得截取路径、忽略裸文件名或由测试代码中的关键字冒充业务实现。
- CLI 报告：CLI 默认渲染结构化任务中文报告，使用中文任务状态和准确的文件操作类型，同一测试目标只展示最新证据；支持 `--output-format json` 输出同一份 `TaskResult` 的 JSON 表示；Agent 默认最多执行 20 轮、调用 40 次工具，并允许通过 `--max-steps` 和 `--max-tool-calls` 调整。
